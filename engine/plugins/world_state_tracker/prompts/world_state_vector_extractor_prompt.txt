### TEMPORAL AUDIT PROTOCOL (MANDATORY)
Before producing `world_state_events`, perform a concise temporal audit of the chapter.

Classify each temporal evidence item as one of:
- `explicit_party_time`: A timestamp or direct clock statement for the current party scene.
- `explicit_offscreen_time`: A timestamp for a Meanwhile, flashback, cutaway, or non-party scene.
- `relative_time`: A relative marker such as "30 minutes ago", "after an hour", "moments later", or "for two hours".
- `sleep_or_overnight_transition`: Characters sleep, go to bed, wake up, dawn arrives, morning comes, or the scene crosses an overnight boundary.
- `travel_time`: The party travels, walks, teleports, rides, sails, or otherwise moves between locations in a way that consumes time.
- `ambient_time_cue`: Sunset, night, stars, moonlight, dawn, morning dew, midday sun, late afternoon, or similar environmental clock evidence.
- `retrospective_reference`: A mention of earlier time, yesterday, last night, the night before, prior sleep, fatigue from lack of sleep, or already-completed events. This explains the current scene but does NOT advance party time by itself.

Rules:
1. `explicit_party_time` overrides estimates and should become a party time anchor.
2. `sleep_or_overnight_transition` is a major time jump unless explicitly contradicted.
3. If the CURRENT SCRIPT shows characters go to sleep/rest for the night and then shows the next party scene in morning/dawn, infer 6-10 hours minimum.
4. If previous time is evening/night and the narrative reaches dawn/morning, the date must advance if needed.
5. Never estimate only the active dialogue/action duration when the chapter crosses a sleep, overnight, dawn, or next-morning boundary. The clock jump dominates the scene duration.
6. `explicit_offscreen_time` and Meanwhile scenes do not advance party time unless the party scene also advances.
7. `travel_time` should be added to the chapter elapsed time when the party performs the travel. Use explicit travel duration when present; otherwise estimate from movement scale.
8. The sum of `world_state_events[*].time_passed_minutes` must be at least the difference between the previous party time and the latest party-current explicit or inferred time.
9. Include the audit in `temporal_audit`. Keep it short and inspectable; do not include hidden chain-of-thought.
10. The PREVIOUS CHAPTER GROUNDING section is already tracked history. Never create `world_state_events` from it. Use it only to decide whether wording in the CURRENT SCRIPT is retrospective.
11. Phrases like "still tired from last night", "from the lack of sleep the night before", "after yesterday", "already awake", or "the previous morning" are `retrospective_reference` unless the CURRENT SCRIPT itself depicts the party sleeping, waking, waiting, traveling, or crossing into a new time period.

### RULES FOR SIMULATION
0. **INITIALIZATION (Turn 1)**:
   - If PREVIOUS_STATE contains null values, you are establishing the baseline.
   - Any weather, time, etc. mentioned is the *starting state*.
   - Assume the story starts at Day 1, 08:00 AM unless the text says otherwise.

1. **Time Inference (CRITICAL)**: 
   - You must calculate the TOTAL minutes passed since CURRENT_DATE. There are 3 common scenarios:
   
   A) NO TIME JUMP: The scene picks up immediately.
      -> Calculation: Just estimate the duration of the scene's actions.
      -> Examples: Dialogue ≈ 15m; Combat ≈ 5m; Exploration ≈ 60m. 
      -> Total = action_duration
   
   B) IMPLIED TIME JUMP: The text implies time has passed (e.g., "The next morning", "after dinner").
      -> Calculation: Estimate the time gap from CURRENT_DATE to the new implied time, PLUS the scene's action_duration.
      -> Example: CURRENT_DATE is 2:00 PM. Text says they went to sleep and woke up the next morning. Jump is ~18 hours. Action duration is 15m.
      -> Total = (18 * 60) + 15 = 1095 minutes
   
   C) EXPLICIT TIME MARKER: The text declares a new time (e.g., "[11:30 AM]", "It is now 9 PM").
      -> Calculation: Calculate the exact minutes from CURRENT_DATE to the LAST explicit time marker in the text, PLUS the action_duration of events happening *after* that marker.
      -> Example: CURRENT_DATE is 02:00 AM. Marker says "9:00 PM". Jump is 19 hours. Scene actions take 30m.
      -> Total = (19 * 60) + 30 = 1170 minutes

      
   **Typical Duration Reference Table**:
   - Short Dialogue/Quick Action: 1-5 minutes
   - Extensive Conversation: 10-30 minutes
   - Combat/Skirmish: 2-10 minutes
   - Short Rest/Meal: 30-60 minutes
   - Exploration/Travel (Local): 30 minutes - 4 hours
   - Travel (Regional): Hours or Days
   - Long Rest/Sleep: 6-10 hours
   - Timeskips: Days, Weeks, Months, or Years

   *Note: Use the unit that makes the most sense (e.g., "5 years" instead of "2628000 minutes").*

2. **Weather/Climate/Safety/Crowd Inertia**: 
   - These values tend to persist. If the text does not mention them, assume they are the SAME as the PREVIOUS_STATE.
   - Only change them if the narrative explicitly describes a change.
   - **Climate**: 
     - Infer the general climate based on the narrative and LOCATION_TAGS.
     - If a tag says "desert", the climate is likely "Hot" or "Arid".
     - If a tag says "arctic", the climate is likely "Freezing" or "Cold".
     - Common values: "Tropical", "Temperate", "Cold", "Freezing", "Hot", "Arid".
   - **Safety Level**: 
     - "Safe": Peaceful, no threats.
     - "Caution": Potential danger, tense atmosphere.
     - "Danger": Immediate threat, hostile environment.
     - "Combat": Active fighting occurring.
   - **Crowd Density**:
     - "Alone": Only the party.
     - "Sparse": A few people around.
     - "Crowded": Many people, busy area.

3. **Inventory Management**:
   - Focus on **narratively significant items**: weapons, equipment, quest items, key documents, or unique valuables.
   - **Ignore mundane clutter**: unless specifically emphasized, do not track generic clothing, dirt, or common environmental fluff.
   - Identify any items obtained, lost, or currently held.
   - Identify any item that was lost, destroyed, or used permanently and remove it from the inventory.
   - Provide the change in quantity (e.g., +1 for gained/starting, -1 for lost).

4. **Indexed Event Rule (CRITICAL)**:
   - Return `world_state_events` with zero-based `line` indexes where world state changes become known.
   - If there are no clear changes, return exactly one event at line 0 that carries state forward with no changes.
   - Always include a line 0 event.
   - Place inventory changes at the first line where the gain/loss/use is known to the player.
   - If a background selector signal aligns with a clear change, prefer the same line index.
   - If no explicit weather/climate/safety/crowd change is present, omit that field in the event instead of inventing values.

5. **Time In Events**:
   - Use `time_passed_minutes` on each event for the amount of time introduced at that line.
   - The sum of all event `time_passed_minutes` is the chapter time progression.
   - For large jumps, reflect realistic amounts from narrative clues and movement context.

6. **Optional Memory Recall Sidecar (RARE)**:
   - You may include `_memory_recall` only when the chapter reveals a durable world-level detail that will help future writing.
   - Prefer zero recalls for ordinary turns. A strong turn usually has one recall; exceptional turns can have two.
   - Do not use this for normal tracker output. Time, weather, climate, safety, crowd density, inventory, and current location already belong in `world_state_events`.
   - Good world recalls are durable consequences, local/world rules, pressures, hazards with future relevance, rumors, altered conditions, taboos, public consequences, or environmental/story meaning that is not represented by the normal fields.
   - Every recall must include a concrete `subject`, `line` or `evidence`, `why_it_matters`, and `not_already_tracked`.
